# 界面返工计划（2026-10-17 用户反馈后）

这份文档是**先量再改**的产物：每一条都带实测数字或可判红的验收标准。
写它的时机是在动手之前——里面有一条是真正的互斥点，需要拍板。

## 0. 先把内存这件事量清楚（决定后面所有"降内存"的说法能不能兑现）

同一台机器（RTX 4060 Ti，15.7 GB 物理内存），release 构建。
探针 = 一个只开窗口、什么都不干的 eframe 应用（`Context::show_viewport_deferred`）。

| 测的东西 | 数 | 怎么量的 |
|---|---|---|
| `fmnr-ui` 单进程常驻 | **104 MB**（Private 115 MB / 10 线程 / 370 句柄） | `Get-Process` WorkingSet64 |
| **裸 eframe 单窗口**（什么都不干） | **64 MB**（private） | 探针 `VPPROBE_N=0` |
| 裸窗口 + 挂中文字体（`simhei.ttf`） | **91–97 MB**（工作集） | 探针 `cjk` 档，两轮 |
| ⇒ **fmnr 自己的全部逻辑**只占 | **约 10 MB** | 104 − 上面那档 |
| release 二进制体积 | 13 MB（debug 是 359 MB） | `ls -l` |
| **点它到窗口出现** | 热 **219 ms** / 冷 1.1–1.8 s | 轮询 `MainWindowHandle` 三轮 |

### 多窗口的真实斜率（这条就是"10 个窗口会不会爆"的答案）

| OS 窗口数（**同一进程**） | private MB | 线程 | 句柄 |
|---|---|---|---|
| 1 | 64 | 12 | 395 |
| 2 | 67 | 12 | 398 |
| 4 | 73 | 12 | 404 |
| 6 | 81 | 12 | 410 |
| **10** | **92** | 12 | 424 |

⇒ 斜率 **3.1 MB / 每个额外窗口**；**线程数不随窗口涨**（一直 12）；句柄 +3.25/窗口。
⇒ **10 个 OS 窗口的裸账 92 MB**；加上每窗口自己的列状态/清单，估 150–250 MB。
**"10 个窗口 ≤1000 MB" 有 4–6 倍余量。**
⚠ 一条要说清楚：`PrivateMemorySize` 不一定计入 D3D/GPU 侧分配
（第二个交换链占的显存可能在这两个计数器之外）。工作集那边 69→71 MB 基本持平是好兆头，
但**不等于已证**——做 §5 时要拿任务管理器的 GPU 列再对一次。


**三条直接结论**：

1. **"几十 M"的地板不是我们的代码，是 GPU 渲染上下文。** 裸开一个窗口就 64 MB
   （wgpu/D3D11 设备 + 交换链 + winit + 系统 GUI 栈），我们的代码只加了约 10 MB。
   ⇒ **你要的"既要几十 M、又要点它快速起来"两个都已经成立**：
   单窗口 64–104 MB、点下去 219 ms（热）。再往下砍只有一条路：不走 GPU，
   而那恰好会砍掉"连贯的无损拖入"。**这是本批唯一一处真互斥**，见 §5。
2. **中文字体值 ~18 MB**（91–97 相对 64–78 那一档的差），是可拿回的最大一块
   （字体文件整份常驻 + 字形图集）。⇒ 见 §6，做字形子集/按需驻留，预计省 10 MB 上下。
3. **"同进程多 OS 窗口"这个选型被实测证明是对的**：一份底子养 10 个窗口（92 MB）。
   反过来若选"多个独立进程"，10 个就是 10×64 MB（裸窗口）到 10×104 MB（fmnr 现状），
   **直接顶破你给的 1000 MB 上限**。

## 1. 左侧栏：把"这台电脑"补进去，并给"挂另一块本地盘"一个入口

**问题**（本轮实测到的，不是猜的）：两栏只能看**已挂载的那个卷**。
面包屑最远到盘根，目录树只挂当前 home 的子树，「📦 挂载」只给 归档 / WSL / SSH 三项。
所以从 `local:C:\Users\…` 出发，走到 `C:\Program Files (x86)\…` 这种**同机另一条绝对路径**
在界面上做不到——而 `LocalVolume::resolve` 其实收绝对路径，**缺的只是入口**。

这条缺口直接害到一件事：栏顶那条"这个目录有新版可升"的弱提示，
判定层与数据装载都验过了，**但那一行从来没渲染出来过**，
因为要让它出现就得走进某个"登记了安装位置又在可升级清单里"的目录，
而那些目录正好都在去不到的地方。

**要做**：
- 树顶加一节「这台电脑」：列出真实盘符（`GetLogicalDrives` + 每盘的标签/容量）、
  WSL 发行版、已挂载的归档卷。点盘符 = 把该卷挂上并把两栏切过去。
- 「📦 挂载」对话框加第四项：**本地目录 / 盘**（选一个绝对路径挂成 `local:<路径>`）。
- 保留现有的特殊文件夹（下载/文档/图片/桌面）。

**验收**：从默认启动状态，**三次点击以内**走到 `C:\Program Files (x86)\`；
截图为证。顺带补上那条一直没验的升级弱提示（走到 Radmin VPN / VS Code 目录）。

**结果（2026-10-17 实测，`3cd06e8` CI `conclusion=success`）**：

- 左栏「这台电脑」列出 4 块盘（带标签与剩余容量），点一下即挂上并把两栏切过去。
  从默认启动状态到 `C:\Program Files (x86)\` 用了**一个单击 + 一个双击**
  （点 `C:\` → 双击 `Program Files (x86)`），比"三次点击以内"还短。
- 那条弱提示**第一次真的画出来了**：走进 `C:\Program Files (x86)\Radmin VPN\`
  后栏顶显示「这里是「Radmin VPN 2.0.9」的安装目录，有新版 2.1.4951.1（现装 2.0.4899.9）」，
  三个数字和包管理器那张表逐项对得上。
- 点旁边的「复制升级命令」：系统剪贴板拿到 `winget upgrade --id Famatech.RadminVPN`，
  同时 `Get-Process -Name winget,RadminVPN` 为空——**只复制、不代跑**这条在点击层面也成立。
- 只有真点才暴露的两个缺陷（都已修）：`egui::Label` 默认 Sense 是 hover，
  少了 `.sense(Sense::click())` 时盘符行**点不动**；`switch_volume` 对 Local 卷
  硬编码回 `dirs_home()`，点 D: 显示的是 `C:\Users\…`。

### §1b 追加（2026-10-18）：上面那条"已修"只修了一半

`switch_volume` 改对了，但**树的根**走的是另一个函数 `volume_root()`，
那里还写死 `dirs_home()`。于是切到 `F:\` 之后两栏在 F:\，侧栏却还长在
`C:\Users\…` 上——同一帧里两个真相。两处各算一遍"起点在哪"，修一处漏一处。

- 起点收成**一个**纯函数 `volume_start(kind, id)`：本地卷 = 它自己的根，
  虚拟卷 = 卷根（空路径），解析不出来 = `None` 让调用方回落 home。
  栏的起点和树的根都从它来，结构上不再可能分叉。
  判据 `a_local_volume_starts_at_its_own_root_not_the_home_directory`；
  反证打过：把本地卷那一臂也改成"一律给卷根" ⇒ 报
  `left: Some("")  right: Some("E:\\")`。
- **快速访问改成扁平一节**（放在「这台电脑」下面）。它以前是嫁接进树根那一层的
  （`tree::merge_specials`）；树根一旦不再是 home，那四个就成了谎——
  在 `F:\` 上时"下载"不是 F:\ 的孩子。`merge_specials` 连同它的两条测试一起删掉：
  留着是没人调的函数，而那两条测试量的正是已经不存在的接线。
  点它走 `goto_path`，所以"在别的卷上点下载"会先把本地卷挂回来再落进目录。
- 实测两张画面：点侧栏 `F:\` → 树根变成 `▸ local:F:\` 并列出该盘的孩子；
  在 `F:\` 上点「下载」→ 卷切回 `local:C:\`、左栏落到 `C:\Users\lbx13\Downloads`、
  树根同时变成 `▸ local:C:\`。
- 顺带记一条我自己的误判：第一次点「下载」没反应，我以为是 `.sense()` 那类老坑，
  回去读代码没找到问题——**是注入的坐标偏了一行**（同一批里点 `y=166` 我以为会中
  `E:\`，实际中了 `F:\`）。重新按一行 ~14px 的偏差点 `y=205` 就正常。
  别把"我瞄歪了"记成"它有 bug"。

## 2. 顶部与路径：分清楚"面板"和"对话框"

**问题**：现在 9 个 `egui::Window`（浮动窗）里，只有 5 个该浮动。
用户原话："我的设置，我不希望是预览那种窗口，那种特别难看……
很多东西它也不是预览窗口，分清楚。"

实测清点（`grep -n 'egui::Window::new(' crates/fmnr-ui/src`）：

| 现在浮动 | 该不该浮动 | 理由 |
|---|---|---|
| 包管理器 | ❌ 该停靠 | 它是**工作区**，不是临时问一句 |
| 设置 | ❌ 该停靠 | 同上 |
| 磁盘占用 | ❌ 该停靠 | 同上（且它要变成 treemap，见 §4） |
| 开机自启动 | ❌ 该停靠 | 它是设置的一节，不该是独立窗 |
| 预览/详情（`title` 那个） | ✅ 该浮动 | 真·预览 |
| 目标已存在 | ✅ 该浮动 | 模态对话框 |
| 重命名 | ✅ 该浮动 | 模态 |
| 新建目录 | ✅ 该浮动 | 模态 |
| 挂载卷 | ✅ 该浮动 | 模态 |

**要做**：四个面板改成**停靠区**（右侧可收起的一栏，或底部一栏，二选一实现后定），
带自己的标题条与关闭按钮，但**不能拖、不能盖住文件列表、不会飘到别的窗口后面**。
设置那一节把「开机自启动」并进去（它本来就是设置的一个开关）。

**验收**：打开设置后，文件列表**不被遮挡**、窗口不产生可拖动的浮动件；
截图两栏 + 停靠面板同时在位的画面。

**结果（2026-10-17 实测）**：四个浮动窗收成**一个右侧停靠栏**，同一帧最多一个
（`Dock` 枚举 + `open_dock`：两个右侧栏并排会把中间的文件列表挤没，而那正是这轮要修的东西）。
「开机自启动」并进设置，成为「这台机器上的启动项」一节；顶栏那个入口留着，
但它开的是设置停靠区，不再有自己的窗。实测三张画面各自成立：
设置 / 磁盘占用 / 包管理器占右侧一栏，两栏列表始终可见；点「关闭」即收起。

两个只有真跑才看得见的缺陷（都已修）：
标题条上的 `✕` 在本机字体栈里**没有字形**，画成一个空方框，看不出它是"关掉"——
改成「关闭」两个字；从「设置」进来时启动项那一节是**空的**（`open_settings` 没读那份清单，
只有 `open_startup` 读），现在两个入口都会读。

⚠ 顺手记下但**没动**的一处同类缺陷：`app.rs` 里过滤框的清除按钮也用 `ui.button("✕")`，
按同一把尺它大概率也是空方框；本轮没点到过它（过滤器是空的），所以不当已证。

## 3. 路径栏：现在比 Windows 差在哪，具体到条目

- 面包屑现在只能点，**不能编辑**、不能整段复制、不能一键复制路径。
- 盘根/UNC/归档卷三种路径的显示形状不统一（`E:\` vs `\\wsl.localhost\…` vs `archive:…\x.zip\…`）。
- 长路径没有中间省略（`C:\Users\…\深层\目标`），会挤掉后面的按钮。

**要做**：面包屑可切换成"可编辑路径框"（回车跳转，和 Windows 点空白处一致）、
每段可右键复制、加"复制当前路径"、长段中间省略。
**验收**：三种卷各截一张图，路径可读且能复制；编辑框贴 `\\wsl.localhost\Ubuntu-24.04\` 回车能进。

**结果（2026-10-17 实测）**：

- **可编辑**：双击栏头 → 变成路径框（带当前值、全选态），回车走，Esc 回原样。
- **回车会换卷**，不只是在当前卷里走：贴 `E:\tmp` → 挂上 `local:E:\` 并落进 `E:\tmp`；
  贴 `\\wsl.localhost\Ubuntu-24.04\home` → 挂上 `wsl:Ubuntu-24.04` 并列出 `home`（实测两条都一次到位）。
  这一步的判据在 `volume_for_path`：盘符一律归一成 `E:\`（**带尾分隔符 + 大写**），
  因为卷 id 是 `local:<路径字符串>`，`e:\` 和 `E:\` 会在注册表里长出同一个盘的两个影子卷。
- **复制**：面包屑行尾「复制」→ 系统剪贴板拿到 `C:\Users\lbx13`（实测 `Get-Clipboard` 对得上）；
  每段右键「复制这一段」→ 拿到的仍是**整条路径**而不是那个标签。
- **中间省略**：`C:\Users\lbx13\.codex-batch-delete-backup-20261009` 在窄栏里画成
  `C:\…codex-batch-delete-backu…`。⚠ 说清楚它的边界：省略号是我们掐的，
  但**尾巴仍会被 egui 的 `.truncate()` 二次截掉**——末段本身比栏宽还长时就是这样。
  信息没丢（面包屑那行会换行把整段写全，状态栏也给全路径），但别把它说成"长路径完整可读"。
- 三种卷的形状：本地 `C:\` / `E:\`、WSL `\\wsl.localhost\Ubuntu-24.04\home` 各截到了；
  **归档卷这一轮没重拍**（注入的点击落到了对话框下面，没换到「归档」页签）。
  它不是新主张：M7a 已实测过归档挂载，而虚拟卷根的形状本轮在 WSL 那一屏就看到了——
  第一跳的标签是「卷根」而不是一个路径。

⚠ 一把尺子在这轮被证明是坏的，记下来：Windows 上 `Path`/`PathBuf` 的 `Eq`
**会把盘符大小写归一**（`PathBuf::from("e:\\") == PathBuf::from("E:\\")` 实测为真），
所以拿它断言"归一成大写"永远量不出来。改成比 `to_string_lossy()` 之后，
去掉 `to_ascii_uppercase()` 的变异才判红。

## 4. 磁盘占用：从线性占比条改成 treemap（非线性）

**这条几乎不要额外内存**——占比条用的已经是"当前层每个子目录一个累计值"这份数据，
换成 squarify 布局只是**换个画法**：同样的输入，画成矩形而不是画成条。

⚠ 但有一条量纲必须写死，否则会被误做成全盘视图：
`docs/UI-NEXT.md` §3.3 实测 disktree 那种**整棵树常驻**是 `Node` 88 B × 条目数，
340 万条目 ≈ **299 MB**。⇒ **只画当前层 + 点进去重扫**（现有下钻语义不变），
不做"一次扫完整块盘再画"。这条边界在代码里要有测试钉住（扫描只保留当前层的累计值）。

**验收**：同一目录下，矩形面积比例与占比条的百分比一致（可以拿数字对拍）；
hover 高亮、单击下钻、右键菜单在矩形上都能触发；窗口缩到很小不破版。

**结果（2026-10-18）**：画法换成 squarify（新模块 `crates/fmnr-ui/src/treemap.rs`，
纯几何不碰 egui，7 项测试），占比条那套 `bar()` 整个删掉。

- **面积一致这条是量出来的，不是看出来的**：`cell_areas_are_proportional_to_weights`
  断言每格面积/总面积与权重比误差 <2%；`cells_tile_the_box_without_gaps_or_overlap`
  断言铺满且两两交集≈0（四组输入，含 37 项的长尾）。
- **"非线性"有专门的判据**：`many_small_items_stay_near_square_instead_of_becoming_slivers`
  ——100 个等权项在 100×100 里最差长宽比 ≤3。反证打过：把贪心扩行改成"一行一个"
  （等于切片式画法）→ 该测试报 **100**，另一条同时报 2040。
- **只画当前层**的边界本来就有测试钉着（`usage.rs` 的 `scans_a_real_tree_and_bins_it`：
  树里 3 个目录但只有 2 个成桶），本轮把"为什么是 2"写进那条测试的注释里，
  并指回 §3.3 那个 299 MB 的实测数。
- 真跑一张：`C:\Users\lbx13` 扫到 19.3 万文件时画出 `.cargo 2.9 GB·24.8%`、
  `.qoder 2.1 GB·17.8%`、`.cache 1.7 GB·14.4%`、`.codex 1.3 GB·11.3%`、
  `.codex.backup-… 1.1 GB·9.4%`、`.agent-browser 535.8 MB·4.5%`，
  长宽比看着就是方的，标签和百分比都画得下。

⚠ **本轮没验到的部分要说清楚**：hover 高亮、单击下钻、右键菜单**在矩形上**这三件事
没能在真窗口里点到——不是代码问题，是这轮跑到这里时输入注入坏了：
`SetCursorPos` 报 0x800700CB，`activate_window` 报"目标窗口无法置前"，
前台被另一个程序（`WorkBuddy.exe`）占着不放。截图能拿（走的是图形捕获，不需要焦点），
鼠标键盘进不去。
两个机制本身这轮在别的控件上验过（面包屑的 `context_menu`、盘符行的 `clicked()`），
但**"接在 treemap 格子上"这一层是推断，不是实测**。下一轮能拿到鼠标时要补点。

## 5. 同进程多 OS 窗口（用户拍定）—— 第一半已实测，只剩跨视口拖拽

**已定**：一个进程开多个 OS 窗口，可散开、可分屏，每窗口有自己的两栏/卷/选择状态。

✅ **第一半测完了（2026-10-17，探针 `VPPROBE_N`）**：
- `Context::embed_viewports() == false` ⇒ 本机 wgpu/D3D11 + windows-gnu 这套栈
  **支持多视口**，不需要走 Embedded 兜底；
- 跑起来 `list_windows` 数到两个**独立 OS 窗口**（标题 `vpprobe` 与 `子窗口`），同一进程；
- 斜率实测 **3.1 MB / 每个额外窗口**、线程数不涨（见 §0 那张表）⇒ 10 窗口裸账 92 MB。
⇒ **原来那个"要不要接受独立进程退路"的问题不用拍了 —— 退路不需要。**

⏳ **只剩一条没测**：**跨视口拖拽**（从 A 窗口拖一个文件到 B 窗口）。
egui 的拖拽载荷挂在共享 `Context` 上，理论上跨视口可用，但"理论上"不算证据。
⇒ 这条要在真 fmnr 上做：开两个窗口、互拖一个文件、截图，
判据是**盘上真的移动了**且两边栏都刷新；只"看起来放下了"不算过。

## 6. 降内存的具体抓手（按可省量排）

1. **中文字体 18 MB**：字形图集按需烘焙已有，但字体文件整份常驻。
   可做：启动只驻留**常用字子集**，缺字再回源补（要读文件就慢一点，但省常驻）。
   预计省 ~10 MB。
2. **每窗口内容预算**：多窗口后，列缓存/缩略图/预览缓冲要按窗口配额，
   不能每窗口各留一份全量。缩略图缓存要有字节上限（现在有没有上限**待查**）。
3. **白板/占用扫描/重复扫描**三个后台任务的缓冲不要同时驻留。
4. **不做**：换软件渲染去省那 73 MB——见 §0 第 1 条，它和"连贯拖入"直接互斥。
