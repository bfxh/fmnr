## 3. 跨设备连接：这条撞了 DESIGN 的非目标，需要你明确拍板

`DESIGN.md` 第 70 行写着 **非目标：不做文件内容同步（OneDrive/Dropbox 类）**。
你要的"手机/电脑/安卓的库能分享""双方装了就直接连"就是这件事的一侧（局域网 P2P，
不是云），但它会把项目从"单机文件管理器 + 远程卷"推到"同步系统"，
这是**产品定位的改变**，不是加一个功能。我不替你改定位，所以先摆事实。

### 3.1 "装了就能互相发现"在局域网内成立，但要按平台付钱

- **iOS**（✅ Apple TN3179 原文权限表）：`.local` 解析、Bonjour 注册/浏览、
  **发出 UDP 单播**都要用户点"本地网络"授权（iOS 14+，macOS 15+）；
  裸多播和"浏览任意服务类型"还要 `com.apple.developer.networking.multicast`
  entitlement，**该授权需 Apple 事先批准**。后台且连接未决时系统**静默拒绝**，
  且**没有任何 API 能查询权限状态**。Apple 自己的建议是：要发现就写 Bonjour，别自己发广播。
- **Android**（✅ 官方文档）：Wi-Fi 栈默认丢弃非本机地址的组播包，必须
  `CHANGE_WIFI_MULTICAST_STATE` + `MulticastLock`；**Android 17（API 37）新增
  "Local Network Protections" 运行时权限**，把本地网络访问整个关到门后。
  ⇒ 这条直接改变"装了就连"的假设：未来两端都会弹权限，而不是自动通。
- **Windows**（✅ MS 网络博客）：Win10 1703 起内置 mDNS，但**企业可用组策略关掉**；
  公共网络档下网络发现默认不通。
- 🔶 AP 客户端隔离 / 企业 VLAN 挡多播是业界常态（无权威统计）。
  ⇒ **结论：发现层必须有兜底**（手输地址 / 扫码 / 复用已有的 SSH 主机表），
  不能把"自动发现"当唯一入口。

### 3.2 跨 NAT 做不到纯无服务器

✅ iroh 官方文档写明：relay 负责初次会合与打洞信令，打洞失败即回落 relay
（自称约 9/10 成功，严格企业网/蜂窝网会失败）。
Rust 现状：`iroh` 1.3.0（62 个直接依赖，官方声明支持 iOS/Android/Win/mac/Linux）、
`libp2p` 0.57.1（45 个直接依赖，面向 DHT/公有网）。
🔶 这个场景选 iroh，不要 libp2p（多出来的复杂度用不上）。
但"自托管 relay"就是一台服务器 ⇒ **"只要装了双方就直接连"这句话在跨网必须降级成
"装了 + 同一个共享码或自有 relay"**。
🔶 风险预告：iroh/quinn 在 windows-gnu 上可能撞上 russh 那类 aws-lc-rs 构建墙
（本仓注释里记过），要先量。

### 3.3 "强制所有都连接"——这段请直接当结论看

> 如果"强制全连"指"装了同一个软件就互相信任"，它在密码学上等于**取消认证这一步**。
> 具体会出四件事：
> 1. **发现层不可信**：mDNS/DNS-SD（RFC 6762/6763）**没有任何认证**。同一 Wi-Fi 上
>    任何设备都能应答别人的查询、伪造主机名和服务端口，把流量指到自己身上。
> 2. **没有配对码就没有 MITM 防护**：跳过带外验证（指纹/二维码/一次性码），
>    等于让"我们连上了同一个路由器"充当信任来源——而这条链路本身被 Wi-Fi 层的
>    已知缺陷击穿（KRACK 2017；FragAttacks，USENIX Security 2021 ✅）。
> 3. **公共 Wi-Fi 不是内网**：在咖啡厅/机场/酒店，"局域网内"= "任意陌生人"。
>    把共享库开给整个网段，等于把家目录对外挂出去。
> 4. **"强制全连"还放大横向移动面**：一台手机被控，凭这个自动互信就能读写你所有
>    其它设备，而且**无法事后归因是谁改的**。

正确的做法是把**"自动"和"信任"分开**：自动发现可以有，只做候选列表；
首次连接必须配对（一次性码或扫码），之后证书指纹钉死；共享按网络分档（家庭/公司/公共）。
✅ Syncthing 就是这个模型：设备 ID 是自签证书指纹、连接时逐个比对白名单、
全流量 TLS——它宁可让用户手动"添加设备"，也不做自动互信。

### 3.4 冲突模型：用版本向量 + 冲突副本，不要用 CRDT

- **裸 last-writer-wins**：手机离线改过、电脑也改过 ⇒ **静默丢一份**。文件管理器不能接受，排除。
- **版本向量**：✅ Syncthing v0.11 起把整型版本换成 version vector，官方 release notes
  原话是"终于有真正的冲突检测"；检测到并发就把输者重命名成 `.sync-conflict-…`
  而**不自动合并**。已知局限（✅ issue #10349）：版本向量只表达因果，
  **不告诉你哪份"更新"**；元数据被外部改动还会误报。⇒ 这与"文件管理器"最贴合：
  粒度是整文件，冲突 = 留两份让用户挑。
- **CRDT**（✅ Shapiro et al., INRIA RR-7687, 2011）：价值只在**结构上可合并**的数据
  （文本树、JSON、笔记）。对 zip/视频/任意二进制整文件，收敛出来的还是"选一份"，
  **白付复杂度**。🔶 唯一例外是笔记/文档类，可按文件类型分流，属后期。

## 4. 该做但有硬边界的四条

### 4.1 卸载 + "可选删个人信息"：这个开关**不可靠实现**

- ✅ `QuietUninstallString` 是**注册表里的可选值**（MSI 文档），安装器作者不给就没有。
  MSI 静默卸载走 `msiexec /x {GUID} /qn /norestart`——**省掉 `/norestart` 会静默重启**，
  退出码 3010 = 待重启。
- ✅ Inno Setup 的卸载器默认只删**安装清单里登记过的文件**（`[UninstallDelete]` 决定额外删什么）；
  而"是否删除配置"那个交互页在 `/SILENT` 下**被跳过，行为由作者定**。
  ⇒ 也就是说"静默"和"保不保留数据"两件事互相纠缠，且**没有统一规则**。
- ❌ **没有找到权威清单说明哪些静默参数会连带删用户数据**。
- 个人数据物理上散在：Known Folders（AppData 三档 Local/Roaming/LocalLow、Documents）、
  `ProgramData`、`HKCU\Software`、开始菜单快捷方式（✅ MS Known Folders 文档）。
  **没有任何标准声明"哪个目录属于哪个应用"** ⇒ 无法确定性判定。

**能做到的版本**（诚实且有用）：卸载后**启发式列残留**——同名 AppData 目录、
`HKCU\Software` 同名键、`.lnk`、`ProgramData` 同名目录——**逐项勾选**，默认全不勾，
并显示每一项的体积与"这是猜的"标记。只有 MSIX 包模型能做到确定性清理
（🔶 per-package 数据容器随卸载清除，未逐页核验原文）。

**判据**：残留识别必须做到"宁可漏报不可误报"——用"目录名与 Publisher/DisplayName
精确匹配 + 位于 Known Folder 之下"双条件，误报率要有语料可量（本机 273 条已装做分母）。

### 4.2 安装包自动下载：可以做，但**只下载不执行**，且默认关

这条的风险不是"能不能"，是它开了一条**自动获取可执行文件**的路。
必须满足：来源固定（包管理器给的安装源 URL，不自己拼）、校验哈希（包管理器清单里有就比对）、
下载到隔离目录、**永不自动运行**、UI 上默认关闭且一开就看得见状态栏有东西在跑。
本机实测：273 条已装里带 URL 的只有 66 条，指向 GitHub 仓的只有 6 条 ⇒
"自动找到安装包"的覆盖面本身就很小（见 §4.4 同一批数字）。

### 4.3 "文件需要钥匙"：这句话里是两个不同的东西

**(a) 防止并发写**（真·文件锁）：✅ Windows `LockFileEx` 是 OS **强制**的字节区间锁，
而 `CreateFile` 的共享模式才是主闸；POSIX 侧 `flock`/`fcntl` 都是**建议锁**（man7 原文）。
Rust 现成件：`fs2`、`fd-lock`、`windows-rs`。这条便宜、无风险，可以做
（预览/编辑时锁住，避免外部程序同时写）。

**(b) 加密**（口令派生密钥）：
- ✅ KDF 底线按 OWASP：Argon2id 19 MiB / t=2 / p=1（静态加密建议上调，🔶）。
- **必须写进设计的诚实结论：口令丢了数据就没了。**
  ✅ Cryptomator 的恢复机制是"另发一把 recovery key"——那等于把裸密钥托管给你自己抄下来；
  gocryptfs 是"打印 masterkey 当恢复凭据"；VeraCrypt 无口令恢复。
  任何"忘记口令也能开"的方案都必然引入**第三方信任**，那是另一个产品。
- 🔴 **和 DESIGN 第 111 行直接冲突**：「枚举目录、读文件、画图标全在进程内」。
  加密卷要出缩略图、要预览、要全文搜索，就必须在**解密态**生成索引——
  **索引本身就是一份明文副本留在盘上**。
  ✅ 这不是能绕的实现问题：可搜索加密（SSE）学界已证明访问模式/搜索模式泄露
  可被实用攻击还原内容（Oya et al. USENIX Sec'21；Stefanov NDSS'14；综述 ACM CSUR 2023），
  连 Dropbox 都公开承认端到端加密 ⇒ 牺牲服务端搜索。
  ⇒ **唯一自洽的设计是：加密卷只在"解锁会话内"可搜可预览，锁上即焚（索引不落盘）。**
  别去找 SSE，那是死路。

### 4.4 重复文件：阶梯与"删前必须字节确认"

- 正确性阶梯：**按大小分组 → 部分读哈希 → 全文件哈希 → 字节比对**。前三级只是筛选项。
- ✅ **删之前必须做字节确认**：jdupes 手册明言哈希碰撞有"小而显著的风险"，
  字节对比是它的显式 failsafe；fdupes/dupeguru 默认同款。
  理论侧：MD5 选择前缀碰撞（Stevens 2009）、SHA-1 实际碰撞（SHAttered 2017）证明
  "构造得出碰撞"不是纸面风险。
  ⇒ 只在"展示嫌疑组、由人来删"时强哈希才够；**任何自动删都要过字节门**。
- 缓存"记住"这件事的锚点：✅ `mtime + size` 会漏（改内容不改时间戳、FAT 2 秒粒度、
  同尺寸改写）。可靠锚是 **NTFS 文件 ID**——Raymond Chen 建议"卷序列号 + `FileIdInfo`
  (`FILE_ID_128A`)"判同一文件；USN Journal 能扫变更但是**环形日志会 wrap**
  （✅ fsutil usn 文档 + 实例）。Windows Search 索引没有稳定的逐文件接口。
  ⇒ 缓存键 = `(卷序列号, FileId, mtime, size)`，四元组任一变了就重算；
  并且**必须允许"不记住"**（你说的），即缓存可一键清空且默认不跨重启。
- CDC（内容定义分块，✅ FastCDC USENIX ATC'16；综述 arXiv:2409.06066）解决的是
  **相似文件切块去冗余**，做"整文件是否重复"是白付每字节 CPU + 块索引库。
  ⇒ **重复文件检测不用 CDC**；CDC 的位置在归档（§5）。

## 5. 7z 与"比它更强"：一半该做，一半永久不做

### 5.1 融入 7z 不是难点

✅ crates.io 实况：`sevenz-rust2` 0.24.0（2026-10-11 更新，`sevenz-rust` 的续维护 fork）
**读+写都有**，LZMA/LZMA2 走 `lzma-rust2`，支持 solid 块、AES-256、BCJ、delta；
底层 `lzma-rs` 0.3.0 **停在 2023-01** 且自述以解码为主；多核写有 `sevenzip-mt` 0.2.2
（自称产物兼容官方 7-Zip，但 0.2.x = 年轻项目）。
🔶 README 未声明多线程与 BCJ2 可用，别假定。
⇒ 这是**几周级的接线工作**。DESIGN 第 280 行那句"7z 未实现（今天没有可验证的需求）"
现在有了需求，可以去掉这条 TODO 了。

### 5.2 "更强"只有三条可验证的轴，其中一条是净负收益

| 轴 | 事实 | 判断 |
|---|---|---|
| 压缩率 | ✅ PeaZip 基准（303 MB 混合样本，**厂商自测、单一数据集**）：ZPAQ ultra 19.01% vs 7z LZMA2 23.50% vs RAR best 25.78%；压缩 359 s vs 137 s，**解压 358 s vs 3.4 s（约 100×）** | 再强只有 15–20%，代价是解压慢两个数量级。对文件管理器是**净负收益** |
| 速度 | ✅ zstd 是唯一有 IETF 标准的现代格式（RFC 8878：帧/可跳过帧/字典）；字典对小数据增益 2–5×（Meta 工程博客）。✅ 7-Zip 官方帮助：LZMA2 "can be divided to independent blocks" ⇒ 块级并行编解码成立 | 可做"边扫边压/增量"。🔶 但单条流内部并行解码仍是论文课题（ACEAPEX），**不写进承诺** |
| 健壮性 | ✅ **7z 没有恢复记录**，RAR 是主流格式里唯一内建的；7-Zip 的 PAR2 集成至今是 open feature request。✅ Rust 侧有 `par3-rs` 0.7.1（读/验/建/修，2026-10 活跃） | **这是唯一能立刻做出可测量优势的地方**，而且是 7-Zip 自己给不了的 |

❌ 未找到 brotli 与 LZMA2 在通用文件上的量化差距的一致口径（brotli 的优势在 web 文本的静态字典，不适合归档）。

### 5.3 落点：不重造压缩器，做"内容寻址 + CDC 的去重式归档卷"

名字与来源：CDC 分块（✅ FastCDC ATC'16）、备份流双模态分块（✅ Bimodal CDC for Backup Streams, FAST'10）、
内容寻址存储（✅ Venti, FAST'02）、系统先例（✅ restic 用 Rabin 滚动哈希）。
Rust 有 `fastcdc` 5.0.0（2026-08）。

卖点变成两件**可测、可回归**的事：
1. "同一卷里第 N 次改动的成本 ≈ 一个 chunk"（可量：改 1 MB 后重写字节数）；
2. "每个块自带校验，卷可验可自愈"（可量：注入坏块后能否修复）。

**永久不做**：自己写 LZMA2/PAQ 级压缩器。三条具体理由——
上限被 §5.2 钉死在 15–20% 且被解压 100× 惩罚吃掉；正确性只能靠与官方 7-Zip 的
**字节级互通语料**（我们手上没有）；`lzma-rs` 六年不动本身就是信号——
纯 Rust 压缩核的维护成本远超一个文件管理器的带宽。

## 6. "MCP 支持太弱"——这条前提不成立，我读了代码

✅ 代码事实：`crates/fmnr-ai/src/tools.rs` 的 `dispatch_payload` 是**唯一分发表**，
MCP（stdio）、HTTP（axum）、CLI 三条入口都走它——MCP 只是把它包一层 `content` 信封，
CLI/HTTP 直接用 payload。当初这么设计就是为了不出现"CLI 能删、MCP 不能"。
⇒ **"不需要 MCP 也能轻易调用"这件事已经成立**，HTTP 还默认锁回环。

真正缺的是三样，都不是协议问题：

1. **内核有、工具表没有**：`Volume` 的 `read_stream`/`write`、属性、建目录/改名，
   以及 `fmnr-pkg` 的已装清单（`quiet_uninstall_string` 字段已经在结构体里了）
   ——**任何一条入口都调不到**。这是覆盖面缺口，不是 MCP 弱。
2. **多卷只在 CLI 有**：MCP/HTTP 进程只挂单个本地卷，归档/WSL/SSH 的注册表没接过去。
3. **摩擦**：CLI 每条命令重新 spawn 进程 + 重扫挂载；没有批量入口、没有 NDJSON/stdin 流式、
   长操作没有进度回传。

⇒ 你缺的是"**更多内核能力上表 + 更少的调用摩擦**"。
修法按性价比排：① 把缺的能力补进 `dispatch_payload`（一处补，三条入口同时获得）；
② MCP/HTTP 复用 `fmnr-mount` 的挂载表；③ CLI 加 `--batch`（stdin 一行一条 JSON）+ 进度走 stderr。

## 7. 设置面板"很大"与桌面中转站

- **设置**：现在只有一个塞了自启动/隐藏项/计数的窗口。要"大"就得先有**分类骨架**
  （外观 / 列表 / 卷与挂载 / 包与更新 / 系统集成 / 高级），
  每节里的开关都必须**已经存在后端**——不做"先摆一排灰开关"那种面板。
  这条属于"有明确做法、只是没人做"，代价小，可以排在下一批。
- **桌面中转站**（"没有主次只分"）：我理解成"一个常驻的落点：拖进来就能分诊
  （归档/上传/转给别的设备/记住）"。它依赖 §3 的连接能力和 §4 的分诊规则，
  在跨设备没定下来之前做等于给空气做 UI。**超级后期，不进近期计划。**

## 9. 需要你拍的三件事

1. **跨设备同步要不要做**？它撞 `DESIGN.md` 第 70 行的非目标。做 ⇒ 定位从"单机文件管理器
   + 远程卷"变成"含同步的文件系统工具"，且要接受"发现自动、信任必须配对、跨网要 relay"
   这三个不浪漫的前提。**不做** ⇒ §3 整节归档为"已调研，暂不采用"。
2. **加密要不要做**？做了就必须接受"加密卷只在解锁会话内可搜可预览，锁上即焚"，
   否则索引是一份明文副本躺在盘上。这条和"全在进程内"是**互斥承诺**，不能都要。
3. **压缩率要不要追**？我的建议是不追（§5.2 那 15–20% 换 100× 解压惩罚），
   把力气放在**恢复记录 + 去重式归档**这两条能量出数字的地方。
