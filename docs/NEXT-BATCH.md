## 3. 跨设备连接：这条撞了 DESIGN 的非目标，需要你明确拍板

`DESIGN.md` 第 70 行写着 **非目标：不做文件内容同步（OneDrive/Dropbox 类）**。
你要的"手机/电脑/安卓的库能分享""双方装了就直接连"就是这件事的一侧（局域网 P2P，
不是云），但它会把项目从"单机文件管理器 + 远程卷"推到"同步系统"，
这是**产品定位的改变**，不是加一个功能。我不替你改定位，所以先摆事实。

### 3.1 "装了就能互相发现"在局域网内成立，但要按平台付钱

- **iOS**（✅ Apple TN3179 原文权限表）：`.local` 解析、Bonjour 注册/浏览、
  **发出 UDP 单播**都要用户点"本地网络"授权（iOS 14+，macOS 15+）；
  裸多播和"浏览任意服务类型"还要 `com.apple.developer.networking.multicast`
  entitlement，**该授权需 Apple 事先批准**。后台且连接未决时系统**静默拒绝**，
  且**没有任何 API 能查询权限状态**。Apple 自己的建议是：要发现就写 Bonjour，别自己发广播。
- **Android**（✅ 官方文档）：Wi-Fi 栈默认丢弃非本机地址的组播包，必须
  `CHANGE_WIFI_MULTICAST_STATE` + `MulticastLock`；**Android 17（API 37）新增
  "Local Network Protections" 运行时权限**，把本地网络访问整个关到门后。
  ⇒ 这条直接改变"装了就连"的假设：未来两端都会弹权限，而不是自动通。
- **Windows**（✅ MS 网络博客）：Win10 1703 起内置 mDNS，但**企业可用组策略关掉**；
  公共网络档下网络发现默认不通。
- 🔶 AP 客户端隔离 / 企业 VLAN 挡多播是业界常态（无权威统计）。
  ⇒ **结论：发现层必须有兜底**（手输地址 / 扫码 / 复用已有的 SSH 主机表），
  不能把"自动发现"当唯一入口。

### 3.2 跨 NAT 做不到纯无服务器

✅ iroh 官方文档写明：relay 负责初次会合与打洞信令，打洞失败即回落 relay
（自称约 9/10 成功，严格企业网/蜂窝网会失败）。
Rust 现状：`iroh` 1.3.0（62 个直接依赖，官方声明支持 iOS/Android/Win/mac/Linux）、
`libp2p` 0.57.1（45 个直接依赖，面向 DHT/公有网）。
🔶 这个场景选 iroh，不要 libp2p（多出来的复杂度用不上）。
但"自托管 relay"就是一台服务器 ⇒ **"只要装了双方就直接连"这句话在跨网必须降级成
"装了 + 同一个共享码或自有 relay"**。
🔶 风险预告：iroh/quinn 在 windows-gnu 上可能撞上 russh 那类 aws-lc-rs 构建墙
（本仓注释里记过），要先量。

### 3.3 "强制所有都连接"——这段请直接当结论看

> 如果"强制全连"指"装了同一个软件就互相信任"，它在密码学上等于**取消认证这一步**。
> 具体会出四件事：
> 1. **发现层不可信**：mDNS/DNS-SD（RFC 6762/6763）**没有任何认证**。同一 Wi-Fi 上
>    任何设备都能应答别人的查询、伪造主机名和服务端口，把流量指到自己身上。
> 2. **没有配对码就没有 MITM 防护**：跳过带外验证（指纹/二维码/一次性码），
>    等于让"我们连上了同一个路由器"充当信任来源——而这条链路本身被 Wi-Fi 层的
>    已知缺陷击穿（KRACK 2017；FragAttacks，USENIX Security 2021 ✅）。
> 3. **公共 Wi-Fi 不是内网**：在咖啡厅/机场/酒店，"局域网内"= "任意陌生人"。
>    把共享库开给整个网段，等于把家目录对外挂出去。
> 4. **"强制全连"还放大横向移动面**：一台手机被控，凭这个自动互信就能读写你所有
>    其它设备，而且**无法事后归因是谁改的**。

正确的做法是把**"自动"和"信任"分开**：自动发现可以有，只做候选列表；
首次连接必须配对（一次性码或扫码），之后证书指纹钉死；共享按网络分档（家庭/公司/公共）。
✅ Syncthing 就是这个模型：设备 ID 是自签证书指纹、连接时逐个比对白名单、
全流量 TLS——它宁可让用户手动"添加设备"，也不做自动互信。

### 3.4 冲突模型：用版本向量 + 冲突副本，不要用 CRDT

- **裸 last-writer-wins**：手机离线改过、电脑也改过 ⇒ **静默丢一份**。文件管理器不能接受，排除。
- **版本向量**：✅ Syncthing v0.11 起把整型版本换成 version vector，官方 release notes
  原话是"终于有真正的冲突检测"；检测到并发就把输者重命名成 `.sync-conflict-…`
  而**不自动合并**。已知局限（✅ issue #10349）：版本向量只表达因果，
  **不告诉你哪份"更新"**；元数据被外部改动还会误报。⇒ 这与"文件管理器"最贴合：
  粒度是整文件，冲突 = 留两份让用户挑。
- **CRDT**（✅ Shapiro et al., INRIA RR-7687, 2011）：价值只在**结构上可合并**的数据
  （文本树、JSON、笔记）。对 zip/视频/任意二进制整文件，收敛出来的还是"选一份"，
  **白付复杂度**。🔶 唯一例外是笔记/文档类，可按文件类型分流，属后期。

## 4. 该做但有硬边界的四条

### 4.1 卸载 + "可选删个人信息"：这个开关**不可靠实现**

- ✅ `QuietUninstallString` 是**注册表里的可选值**（MSI 文档），安装器作者不给就没有。
  MSI 静默卸载走 `msiexec /x {GUID} /qn /norestart`——**省掉 `/norestart` 会静默重启**，
  退出码 3010 = 待重启。
- ✅ Inno Setup 的卸载器默认只删**安装清单里登记过的文件**（`[UninstallDelete]` 决定额外删什么）；
  而"是否删除配置"那个交互页在 `/SILENT` 下**被跳过，行为由作者定**。
  ⇒ 也就是说"静默"和"保不保留数据"两件事互相纠缠，且**没有统一规则**。
- ❌ **没有找到权威清单说明哪些静默参数会连带删用户数据**。
- 个人数据物理上散在：Known Folders（AppData 三档 Local/Roaming/LocalLow、Documents）、
  `ProgramData`、`HKCU\Software`、开始菜单快捷方式（✅ MS Known Folders 文档）。
  **没有任何标准声明"哪个目录属于哪个应用"** ⇒ 无法确定性判定。

**能做到的版本**（诚实且有用）：卸载后**启发式列残留**——同名 AppData 目录、
`HKCU\Software` 同名键、`.lnk`、`ProgramData` 同名目录——**逐项勾选**，默认全不勾，
并显示每一项的体积与"这是猜的"标记。只有 MSIX 包模型能做到确定性清理
（🔶 per-package 数据容器随卸载清除，未逐页核验原文）。

**判据**：残留识别必须做到"宁可漏报不可误报"——用"目录名与 Publisher/DisplayName
精确匹配 + 位于 Known Folder 之下"双条件，误报率要有语料可量（本机 273 条已装做分母）。

### 4.2 安装包自动下载：可以做，但**只下载不执行**，且默认关

这条的风险不是"能不能"，是它开了一条**自动获取可执行文件**的路。
必须满足：来源固定（包管理器给的安装源 URL，不自己拼）、校验哈希（包管理器清单里有就比对）、
下载到隔离目录、**永不自动运行**、UI 上默认关闭且一开就看得见状态栏有东西在跑。
本机实测：273 条已装里带 URL 的只有 66 条，指向 GitHub 仓的只有 6 条 ⇒
"自动找到安装包"的覆盖面本身就很小（见 §4.4 同一批数字）。

### 4.3 "文件需要钥匙"：这句话里是两个不同的东西

**(a) 防止并发写**（真·文件锁）：✅ **2026-10-19 做了，而且不用 `LockFileEx`、不用新依赖**。
- 原判断（"`CreateFile` 的共享模式才是主闸"）是对的，但**方向**要先实测才定得下来：
  Windows 的共享检查是拿**已存在句柄**的掩码去判新来的访问请求，
  而 `std::fs::File::create` 把自己的掩码开成**全共享**——于是往一个"别的程序正开着写"
  的文件上覆盖时，CreateFile 直接成功并 `truncate` 掉对方的字节。
  本机实测（沙盒 `crates/fmnr-fs/tests/share_mode_probe.rs`）：对方以 std 默认全共享
  持句柄、已写 8 字节 ⇒ `File::create` 得到 `Ok`、目标长度变成 **0**；
  换成 `share_mode(READ|DELETE)` 的开法得到 `ERROR_SHARING_VIOLATION(32)`。
  反向也量了：对方只共享读（Explorer/Office 那一类）时 **std 默认开法本来就会失败**，
  所以那一类从来不需要额外做什么。
- **在 fmnr 自己的接口层上量到的修前行为**（沙盒 `concurrent_write_probe.rs`）：
  对方持着写句柄、目标已存在时，`ops::transfer([src], dst, Overwrite, _)` 返回
  `Ok(done=1, skipped=0, bytes=4096)` —— 也就是**整条链路报告"成功"**，
  而对方的内容已经被换掉/截掉。修后同一次调用返回 `Err` 并带那句人话。
  这条是为什么门要建在 `ops` 层而不是只测裸句柄：裸句柄只能证明机制，
  证明不了"用户看到的那句话是假的"。
- 落地的形状：`ops::create_exclusive`（Windows 用 std 自带的 `OpenOptionsExt::share_mode`，
  掩码 `FILE_SHARE_READ|FILE_SHARE_DELETE`）+ `ops::write_file` 这一个唯一入口，
  `copy_file` 与 `LocalVolume::write` 都汇到它；32 号错翻成一句人话
  （"… 正被另一个程序开着写，不能覆盖它（要覆盖请先关掉那个程序）"），
  其余 io 错误原样交给 `Error::Io`——把不认识的错误都改写成"被占用"是另一种撒谎。
  **没有**引 `fs2` / `fd-lock` / 为了两个常数把 `windows` 拉进编译面。
- **刻意没做的一半**：POSIX 没有共享语义可借（`flock`/`fcntl` 都是**建议锁**），
  非 Windows 分支保持 `File::create` 原样，不装出"锁住了"的样子；
- **刻意没做的一半**：POSIX 没有共享语义可借（`flock`/`fcntl` 都是**建议锁**），
  非 Windows 分支保持 `File::create` 原样，不装出"锁住了"的样子；
  **读取/预览侧不加锁**——读了就把别人写死是更糟的取舍，所以
  "文件在预览期间被外部改掉"这一半仍然没处理（登记在这）。
  还有第三格没接上：**fmnr 自己的落盘**（白板 `crates/fmnr-core/src/board.rs:165` 的
  `std::fs::write`）走的仍是默认全共享。它挡不住"两个窗口同时存同一份白板"，
  但把它接进来的正确做法要让 `fmnr-core` 依赖 `fmnr-fs`（方向是反的）或把这条政策
  **复制到第二处**——后者正是本轮 `.lnk` 那条教训的形状（同一句事实写两份，
  一定有一份先过期），所以宁可留空并登记在这里，不做复制。
- 🔴 **界面那一步没单独拍图**：这条新失败走的是既有的操作错误通路（与"权限不足"同一
  条 `Error::Io`/`Error::Other` → 状态行），那条通路本轮之前拍过图，但"目标被别的程序
  占着"这一句具体文案**没有在真窗口里看到过**。要验它需要：另开一个程序以写方式占住
  目标文件，再在 fmnr 里把同名文件拖过去选覆盖。
- 门：`ops::tests::overwrite_refuses_a_file_another_writer_holds`，
  含对照组（没人占用时同一次覆盖必须照样成功，否则这条是空转）。
  变异复打 **4/4 全判红**（沙盒 `mut_lock.py`，红在断言消息上，无崩溃红、无编译不过逃逸）：
  掩码改成 `0x7`（全共享）、整段去掉 `.share_mode(...)`、拆掉 32 号错的映射、
  `write_file` 绕回 `File::create`。

**(b) 加密**（口令派生密钥）：
- ✅ KDF 底线按 OWASP：Argon2id 19 MiB / t=2 / p=1（静态加密建议上调，🔶）。
- **必须写进设计的诚实结论：口令丢了数据就没了。**
  ✅ Cryptomator 的恢复机制是"另发一把 recovery key"——那等于把裸密钥托管给你自己抄下来；
  gocryptfs 是"打印 masterkey 当恢复凭据"；VeraCrypt 无口令恢复。
  任何"忘记口令也能开"的方案都必然引入**第三方信任**，那是另一个产品。
- 🔴 **和 DESIGN 第 111 行直接冲突**：「枚举目录、读文件、画图标全在进程内」。
  加密卷要出缩略图、要预览、要全文搜索，就必须在**解密态**生成索引——
  **索引本身就是一份明文副本留在盘上**。
  ✅ 这不是能绕的实现问题：可搜索加密（SSE）学界已证明访问模式/搜索模式泄露
  可被实用攻击还原内容（Oya et al. USENIX Sec'21；Stefanov NDSS'14；综述 ACM CSUR 2023），
  连 Dropbox 都公开承认端到端加密 ⇒ 牺牲服务端搜索。
  ⇒ **唯一自洽的设计是：加密卷只在"解锁会话内"可搜可预览，锁上即焚（索引不落盘）。**
  别去找 SSE，那是死路。

### 4.4 重复文件：阶梯与"删前必须字节确认"

- 正确性阶梯：**按大小分组 → 部分读哈希 → 全文件哈希 → 字节比对**。前三级只是筛选项。
- ✅ **删之前必须做字节确认**：jdupes 手册明言哈希碰撞有"小而显著的风险"，
  字节对比是它的显式 failsafe；fdupes/dupeguru 默认同款。
  理论侧：MD5 选择前缀碰撞（Stevens 2009）、SHA-1 实际碰撞（SHAttered 2017）证明
  "构造得出碰撞"不是纸面风险。
  ⇒ 只在"展示嫌疑组、由人来删"时强哈希才够；**任何自动删都要过字节门**。
- 缓存"记住"这件事的锚点：✅ `mtime + size` 会漏（改内容不改时间戳、FAT 2 秒粒度、
  同尺寸改写）。可靠锚是 **NTFS 文件 ID**——Raymond Chen 建议"卷序列号 + `FileIdInfo`
  (`FILE_ID_128A`)"判同一文件；USN Journal 能扫变更但是**环形日志会 wrap**
  （✅ fsutil usn 文档 + 实例）。Windows Search 索引没有稳定的逐文件接口。
  ⇒ 缓存键 = `(卷序列号, FileId, mtime, size)`，四元组任一变了就重算；
  并且**必须允许"不记住"**（你说的），即缓存可一键清空且默认不跨重启。
- CDC（内容定义分块，✅ FastCDC USENIX ATC'16；综述 arXiv:2409.06066）解决的是
  **相似文件切块去冗余**，做"整文件是否重复"是白付每字节 CPU + 块索引库。
  ⇒ **重复文件检测不用 CDC**；CDC 的位置在归档（§5）。

### 5.2 "更强"只有三条可验证的轴，其中一条是净负收益

| 轴 | 事实 | 判断 |
|---|---|---|
| 压缩率 | ✅ PeaZip 基准（303 MB 混合样本，**厂商自测、单一数据集**）：ZPAQ ultra 19.01% vs 7z LZMA2 23.50% vs RAR best 25.78%；压缩 359 s vs 137 s，**解压 358 s vs 3.4 s（约 100×）** | 再强只有 15–20%，代价是解压慢两个数量级。对文件管理器是**净负收益** |
| 速度 | ✅ zstd 是唯一有 IETF 标准的现代格式（RFC 8878：帧/可跳过帧/字典）；字典对小数据增益 2–5×（Meta 工程博客）。✅ 7-Zip 官方帮助：LZMA2 "can be divided to independent blocks" ⇒ 块级并行编解码成立 | 可做"边扫边压/增量"。🔶 但单条流内部并行解码仍是论文课题（ACEAPEX），**不写进承诺** |
| 健壮性 | ✅ **7z 没有恢复记录**，RAR 是主流格式里唯一内建的；7-Zip 的 PAR2 集成至今是 open feature request。✅ Rust 侧有 `par3-rs` 0.7.1（读/验/建/修，2026-10 活跃） | **这是唯一能立刻做出可测量优势的地方**，而且是 7-Zip 自己给不了的 |

❌ 未找到 brotli 与 LZMA2 在通用文件上的量化差距的一致口径（brotli 的优势在 web 文本的静态字典，不适合归档）。

### 5.3 落点：不重造压缩器，做"内容寻址 + CDC 的去重式归档卷"

名字与来源：CDC 分块（✅ FastCDC ATC'16）、备份流双模态分块（✅ Bimodal CDC for Backup Streams, FAST'10）、
内容寻址存储（✅ Venti, FAST'02）、系统先例（✅ restic 用 Rabin 滚动哈希）。
Rust 有 `fastcdc` 5.0.0（2026-08）。

卖点变成两件**可测、可回归**的事：
1. "同一卷里第 N 次改动的成本 ≈ 一个 chunk"（可量：改 1 MB 后重写字节数）；
2. "每个块自带校验，卷可验可自愈"（可量：注入坏块后能否修复）。

**永久不做**：自己写 LZMA2/PAQ 级压缩器。三条具体理由——
上限被 §5.2 钉死在 15–20% 且被解压 100× 惩罚吃掉；正确性只能靠与官方 7-Zip 的
**字节级互通语料**（我们手上没有）；`lzma-rs` 六年不动本身就是信号——
纯 Rust 压缩核的维护成本远超一个文件管理器的带宽。

## 6. "MCP 支持太弱"——这条前提不成立，我读了代码

✅ 代码事实：`crates/fmnr-ai/src/tools.rs` 的 `dispatch_payload` 是**唯一分发表**，
MCP（stdio）、HTTP（axum）、CLI 三条入口都走它——MCP 只是把它包一层 `content` 信封，
CLI/HTTP 直接用 payload。当初这么设计就是为了不出现"CLI 能删、MCP 不能"。
⇒ **"不需要 MCP 也能轻易调用"这件事已经成立**，HTTP 还默认锁回环。

真正缺的是三样，都不是协议问题：

1. **内核有、工具表没有**：`Volume` 的 `read_stream`/`write`、属性、建目录/改名，
   以及 `fmnr-pkg` 的已装清单（`quiet_uninstall_string` 字段已经在结构体里了）
   ——**任何一条入口都调不到**。这是覆盖面缺口，不是 MCP 弱。
   ✅ **已做完（2026-10-17）**：`read_file`/`write_file`/`rename`/`create_dir` 见 §11，
   `stat`（属性，走卷给的 `Entry`）与 `packages`（已装底账）见 §19。
   剩 `read_stream` 没单独成工具——`read_file` 内部就是按块读，
   再开一个流式工具对 JSON-RPC 的调用方没有可消费的意义（它拿不到增量）。
2. **多卷只在 CLI 有**：MCP/HTTP 进程只挂单个本地卷，归档/WSL/SSH 的注册表没接过去。
3. **摩擦**：CLI 每条命令重新 spawn 进程 + 重扫挂载；没有批量入口、没有 NDJSON/stdin 流式、
   长操作没有进度回传。
   ✅ **批量入口已做（2026-10-17，见 §20）**：`fmnr batch` 吃 NDJSON、共享一次挂载扫描，
   20 条命令实测 0.813 s → 0.045 s（**18.2 倍**）。
   剩"长操作没有进度回传"没做——批量里放得进 `copy` 这类操作，
   但进度要另开一条流（stderr 的 NDJSON 事件），那是下一个单元，没顺手塞。

⇒ 你缺的是"**更多内核能力上表 + 更少的调用摩擦**"。
修法按性价比排：① 把缺的能力补进 `dispatch_payload`（一处补，三条入口同时获得）；
② MCP/HTTP 复用 `fmnr-mount` 的挂载表；③ CLI 加 `--batch`（stdin 一行一条 JSON）+ 进度走 stderr。

## 12. 门禁第 5 步的可覆盖面是量出来的，不是推的

本机 `x86_64-unknown-linux-gnu` 的 clippy **编不过全工作区**：`ring`（←russh←fmnr-remote）
和 `zstd-sys`（←fmnr-archive）的构建脚本要 `x86_64-linux-gnu-gcc`，这台机器没有跨端 C 编译器。
逐包实跑后的分档写进了 `scripts/gate.sh`：

- 跑得动、必须绿：`fmnr-core fmnr-fs fmnr-pkg fmnr-icons fmnr-plugins fmnr-ai fmnr-bench`
- 跑不动、点名说没判：`fmnr-ui fmnr-cli fmnr-mount fmnr-remote fmnr-archive`
  （它们的非 Windows 编译只有 CI 的 ubuntu job 判得动）

上一版脚本对第 5 步用 `--workspace`，我删掉 `target/x86_64-unknown-linux-gnu` 之后
它就从"绿"变成了"环境判红"——**缓存能掩盖环境缺口**。所以分档必须显式列包名，
不能靠"上次它过了"。

## 17. §6.2 剩下的不是工作量，是一个依赖决定（要你拍）

路由规则已经统一（见 §11 的更新）。但 MCP/HTTP 要**真的**看到归档卷，
`fmnr-ai` 必须能把一个 zip 挂成卷，而挂卷的代码在 `fmnr-mount` →
`fmnr-archive`（`zstd-sys`）与 `fmnr-remote`（`ring`）——**两个都要跨端 C 编译器**。

代价是可测量的，不是"稍微重一点"：
- `fmnr-ai` 一旦吃到这两个依赖，它的 linux 交叉编译就和本机 `fmnr-ui`/`fmnr-cli` 一样
  **过不了门禁第 5 步**（本机没有 `x86_64-linux-gnu-gcc`）⇒ MCP 那一层的
  "非 Windows 才出现的错"从此只能等 CI 判红。今天 `fmnr-ai` 是**在**可覆盖面清单里的。
- MCP server 二进制要带上 zstd + ring 的编译产物；`Cargo.lock` 里 `ring` 目前
  只经 `fmnr-remote` 进来，MCP 用户（很多是 AI 客户端，只想列个目录）会跟着背。

三条路，按代价排：
1. **注入式（不加依赖）**：`fmnr-ai` 的 `Server`/`router` 收一个
   `Arc<VolumeRegistry>`（类型在 `fmnr-core`，零新依赖），谁起服务谁填表。
   今天的 `fmnr-ai` 可执行文件仍是单卷；要多卷就从**已经有多卷的那个进程**
   （UI，或以后带 `--mount` 的 CLI 常驻模式）里起服务。半天，无代价，但"独立跑个 MCP server 就能读 zip"仍然做不到。
2. **只加归档、不加远程** —— ❌ **量过了，省不掉**：
   `cargo tree -p fmnr-archive --target x86_64-unknown-linux-gnu -i zstd-sys` 给出
   `zstd-sys ← zstd-safe ← zstd ← zip 9.0.3 ← fmnr-archive`，是**必经链**，
   不是可选 feature。⇒ 这条与第 3 条同代价，划掉。
3. **全都要**：MCP/HTTP 与 CLI 一样能挂任意卷。代价就是上面那两条（可覆盖面 + 二进制）。

我的建议是 **1 先做**（它把"三个入口共用一份规则"这件事从"规则"推到"进程"，
而且不动依赖树），2/3 等你说值不值那半条门禁覆盖面。

## 18. N2 交付到哪一步、以及为什么刻意没先做缓存（2026-10-17）

> **续篇**：`is` 提交（M9）里"缓存要不要持久化、文件锁做多强"等 6 个待决策项原本写在
> `IS-CONTRIBUTION.md`，该文档已于 2026-10-19 删除（方案未实现且文件地图与仓不符）；
> 其中两条还活着的口子收进本文 §21，其余（磁盘占用增量、拖放进度、插件预览、协议注册回滚）
> 都已以别的形状上线。本节是"N2 阶段刻意没做缓存"的上下文。

`crates/fmnr-fs/src/dupes.rs`：阶梯 `大小分组 → 头尾部分读哈希 → 全文件哈希 → 字节比对`。
前三级只筛"不可能相同"，**只有第四级算判定**——理由写在模块头：
MD5（Stevens 2009）与 SHA-1（SHAttered 2017）都能构造碰撞，
而"同哈希不同内容"被判成重复 ⇒ 用户按清单删掉的是不相等的东西。
jdupes 手册把字节对比写成显式 failsafe，不是可选优化。

**哈希做成参数不是为了灵活**，是为了能喂一个恒等碰撞哈希，
从而把"字节比对这道门真的在挡"写成可判红的测试：
- 碰撞 + 内容不等 ⇒ 不许成组（把 `confirm_by_bytes` 换成"全都算一组"，这条立刻判红）
- 碰撞 + 内容真相等 ⇒ 必须成组（否则上一条可以由"永远不分组"糊过去）
两条合起来才封死偷懒实现。

这一层**只报清单不删东西**：删除走 `ops.rs` 的回收站路径，由 UI 逐项勾选后发起。
读不到的文件进 `skipped` 回传，不静默跳过——一份看起来完整、其实漏了三个文件的清单，
用户会照着删。

### ✅ 缓存已补上（2026-10-17，`fmnr-fs::fingerprint`）
四元组 `(卷序列号, 文件索引, mtime, size)`：Windows 走 `GetFileInformationByHandle`
（`dwVolumeSerialNumber` + `nFileIndexHigh/Low`，字段类型已在本地 crate 源码核对），
Unix 走 `MetadataExt` 的 `dev()/ino()`。**四个分量全部进键**——
第一版把 `size` 漏在键外，被"任一分量变了必须不命中"那条测试当场抓红。
部分读哈希与全文件哈希**分两个槽**（键里带阶段标记）。
"可以选择不记住"是真的开关：`HashCache::ephemeral()` 拒绝落盘并说明原因。
存之前会**再取一次指纹比对**，两次一样才记——否则读取途中被改写的文件
会留下一条"新指纹 → 旧内容哈希"。

⚠ 一条被反证否掉的判据（写在这里免得下次又当成理由）：我原以为
"头尾相同中间不同"那条测试能抓"两级共用一个槽"，实际**抓不到**——
槽位挤在一起只会让全文件那一查拿到短哈希，两个文件拿到同一个错哈希而成组，
接着**字节门把它们分开**。真正咬住那个变异的是命中/未命中计数那条。
⇒ 这条测试的真实作用是纵深防御（缓存喂错哈希也翻不了车），不是槽位隔离的判据。

### 当初为什么先不半成品
用户提过"重复文件可以缓存，可以选择不记住"。但 §4.4 定的锚点是
`(卷序列号, FileIdInfo, mtime, size)` 四元组，而 Windows 上 std 的
`MetadataExt` **既不给卷号也不给文件索引** ⇒ 要 `GetFileInformationByHandle`。
所以缓存是独立的下一单元（任务 #39）。
**这里刻意没留一个"先按 mtime+size 缓存"的过渡版**：
那种缓存会把该重算的判成不用重算（timestomp、FAT 2 秒粒度、同尺寸改写都漏），
比没有缓存更糟。宁可这一轮少交付一半。

## 19. 属性与已装清单上表（2026-10-17）——顺手挖出一个界面缺陷

§6.1 剩下的两条补进 `tools::dispatch_payload`：`stat`（单条目属性）与
`packages`（已装底账），CLI 侧对应 `fmnr stat <路径>` 与 `fmnr apps [--query] [--limit]`。
一处补，三条入口同时拿到——这正是 §6 说的"覆盖面缺口不是 MCP 弱"。

**`stat` 刻意不自己 `fs::metadata`**：属性一律从**卷给的 `Entry`** 里取。
归档卷的"大小"是包内声明的大小、远程卷的是 SFTP 报的，
自己 stat 一遍等于把这套口径换成"只对本地盘成立"的另一套。

### 顺着这条路挖出来的真缺陷：勾上「显示隐藏项」会把属性一起关掉
`fmnr-fs::LocalVolume::list` 里整段属性计算写在 `if !opts.show_hidden { … }` 里面，
所以：
- `show_hidden = true`（界面那个勾选、以及 `stat`）时，`Hidden`/`System`/`ReadOnly`
  **三个标记一起变空**——"显示了隐藏项"反而看不到它是隐藏项；
- 更难看的是 `attrs.push(Attr::Hidden)` 那一行**前面就摆着一个同条件的 `continue`**，
  它在 Windows 上永远到不了：那份代码从来没执行过一次。
- Windows 上 `ReadOnly` 位压根没算过（`FILE_ATTRIBUTE_READONLY` 没读）。
- unix 上判只读用的是 `mode & 0o400`（**读**位），要的是 `0o200`（属主写位）：
  会把"能改但谁都不许读"报成只读、把真只读的漏掉。

`fmnr-archive` 早就是"先算属性、再按开关筛"（`show_hidden || !attrs.contains(Hidden)`）
⇒ 这次是把 `LocalVolume` 对齐到仓里已有的那套口径，不是新发明。
测试：`attr_tests` 两条，各带一个**对照组**（普通文件不许也带 Hidden/ReadOnly），
否则"全都算成隐藏"也能让断言过。反证打过：把 Hidden 的条件改回带 `!show_hidden`
就判红。unix 那条 `0o200` 本机判不动（Windows 没有 mode 位），由 CI 的 ubuntu job 判。

### `packages` 的两条刻意取舍
1. **不回显 `uninstall_string` / `quiet_uninstall_string`**。那是可执行面，
   而本项目的立场是"只列、不代跑卸载/升级"；和"注册动作不做成 MCP 工具"同一条理由
   ——碰系统边界的不由远程客户端触发。给一个 `has_uninstaller` 布尔就够回答"能不能卸"。
   这条由测试钉住：返回体里不许出现那两个字段名。
2. 非 Windows 上 `list_installed()` **报错**而不是回空表
   （"这台机器没装软件"和"这台机器读不到注册表"是两件事）。
   也因为它必然报错，`packages` **没进**三条腿一致性那串序列——
   三条腿报错时的形状本来就不一样（JSON-RPC 的 error 对象 / HTTP 状态码 / CLI 退出码+stderr），
   而那串序列钉的是"成功返回整份相等"。它的接线改由 CLI 侧的
   `every_subcommand_targets_a_registered_tool` 钉。

### 顺带把那条"每个子命令"的测试补成真的
它原来只列了 8 个子命令，而 clap 声明了 16 个——N1 加的 `cat`/`put`/`rename`/`mkdir`
**全都在名单外**，测试名却写着"每个"。现在名单补全，并加一条
`clap 声明数 == 名单数 + 2`（register/unregister 不走工具表）的数量断言：
以后新增变体不往名单里加就当场判红。反证打过：从名单里删掉 `Cmd::Stat` 一项，
报"clap 声明了 16 个但名单只有 13 项"。

### 依赖代价是量过的，不是估的
`fmnr-ai` 新增 `fmnr-pkg` 一条依赖。它只带 `thiserror`/`tracing` 和
**按 target 门控**的 `windows`，不带 `ring`/`zstd-sys` 那两条要跨端 C 编译器的链
⇒ `fmnr-ai` 仍留在门禁第 5 步的可覆盖面清单里（跑过，见门禁输出）。
这和 §17 那条"让 MCP 进程自己挂归档卷"是**两件事**：那条要把 `fmnr-mount`→`fmnr-archive`

## 20. `fmnr batch`：把 §6.3 那条摩擦量出来再削（2026-10-17）

stdin 一行一条 `{"tool":"…","args":{…}}`，stdout 一行一条
`{"line":N,"ok":true,"result":…}` / `{"line":N,"ok":false,"error":{…}}`。
工具名直接就是分发表里那一个，所以批量天然覆盖全部工具，不需要为它再加子命令。

**先量后改**（数字是这台机器、debug 构建、各跑 3 轮取最好一次）：
20 次 `fmnr stat note.txt` = **0.813 s**；一次 `fmnr batch` 喂 20 行 = **0.045 s**，
**18.2 倍**。差的就是 20 次进程 spawn + 20 次重扫挂载。
⇒ "CLI 摩擦大"原来是一句感觉，现在有数了；削掉的也就是那两项。

三个刻意的形状，每个都有测试钉着：
- **一行失败不中断整批**。未知工具、坏 JSON 都只杀它自己那一行，后面的照跑；
  退出码"全成 0 / 有任何一行失败 1"，汇总计数走 stderr 不污染 stdout。
  反证：把实现改成遇错就 `exit(1)`，测试拿到 3 行而不是 5 行，判红。
- **返回体自带 `line`，对齐输入的物理行号**。空行是分隔符：不是一条请求，也不回一行——
  所以消费方不能靠"第 N 个输出对第 N 个输入"，必须靠这个字段。
  反证：把行号改成按输出计数，`[1,3]` 变成 `[1,2]`，判红。
- **`list_volume` 在批量里必须和 `fmnr volumes` 给同一份卷表**。
  分发表那一臂只知道被选中的那个卷，`run_tool` 里原本有一段专门列全表的特例；
  批量若直接喂分发就会静默分叉成"batch 里的 list_volume 只报默认卷"。
  所以把那段抽成 `volumes_payload`，两条路径共用，测试逐字比对两边。

`Ctx::open()`（挂载表 + 默认卷 + 运行时）也是这么抽出来的：
原来那三样长在 `run_tool` 里，批量要么复制一份（就会分叉），要么共用（就得抽）。

## 23. 跨卷互传：把"从压缩包里取一个文件"这条通路接通（2026-10-19）

用户提法是「多系统互传」。落在本仓的形状是**跨卷搬运**（Windows 本地 / WSL / SSH / 归档
都在同一套 `Volume` 抽象上），不是跨设备同步——后者撞 `DESIGN.md` 的非目标"不做文件内容同步"，
那条**没动**。

### 起点是量出来的，不是设想的

```text
$ fmnr cp 'archive:D:\tmp\e2e\pack.7z/hello.txt' --to 'D:\tmp\e2e\out'
fmnr: unsupported: 归档卷是只读的：1 → D:\tmp\e2e\out (-32603)
```

`Volume::copy(sources, dest_dir)` 把**源和目标都在同一个卷里 resolve**，而路由按
`sources` 的前缀选中了归档卷 ⇒ 目标也去那个只读卷里解析。
结论：**四条入口（UI / CLI / MCP / HTTP）没有一条能把压缩包里一个文件取到本地**。

### 做了的六格

1. `Volume::write_stream(dest, stream) -> u64`：与 `read_stream` 对称的**流式写**。
   trait 里带一份默认实现（收齐再 `write`），`LocalVolume` 覆写成边收边写。
2. `fmnr-core::transfer::copy_across(src, dst, ...)`：源 `read_stream` → 目标 `write_stream`，
   一块一次写，两边都不整份进内存。**分两趟**：第一趟把整批问清楚（存在性、是不是目录、
   头表里的 size），第二趟才动手搬——目录的拒绝必须发生在写第一个文件之前，
   而进度条的分母只能从第一趟拿（`fraction()` 在 0 分母下恒报 0.0）。
3. `VolumeRegistry::route_for_dest(dest)`：目标目录属于哪个卷。**第二条路由**，
   与 `route_for` 共用同一份最长匹配规则，只多认一层裸绝对路径（按目录成分比，不按字符串）。
4. 三条入口的「选卷 + 分派」从各写一遍收成 `tools::dispatch_on_registry` 一格
   （以前 MCP/HTTP/CLI 各抄了一份 `route_or_default` + `dispatch_payload`，形状一样但互不相干）。
5. `fmnr-core::rename`：`a.txt → a (2) → a (3)` 这条**命名规则**从 `fmnr-fs::ops::unique_name`
   里提成单独一格，两边共用。理由是跨卷那侧也要用它，而"两份规则各过期一半"是本仓反复踩过的。
6. `VolumeRegistry::route_source(tool, args)`：**选源卷这件事不再看目标**。这是接第 3 格时
   顺手量出来的既有缺陷，见下面"源卷被目标抢走"那条实测。

### 六条实测口径，其中三条推翻我自己写下的说法

- 🔴 **"跨卷 move 要拒绝并解释源侧删除语义"是我先写的，实测把它推翻了。**
  真打变异（让 `move` 也走跨卷特判）时那条门**照样绿**：两个本地卷之间的 `move` 本来就能用——
  `LocalVolume` 认绝对路径，源被解析到另一个盘的根之外，它本来就是一次文件系统级移动。
  在那里加一层拒绝只会把**本来能用的一条**弄坏。所以 `cross_target` 只对 `copy` 生效，
  源真是只读卷时由该卷自己的 `move_entries` 拒（消息"归档卷是只读的"）。
- 🔴 **"整目录提取的前置是 `Volume::search` 跳过隐藏件"也是我先写的，读代码后收回。**
  这条按卷分开才是对的：`ArchiveVolume::search` 走索引、**根本不过滤隐藏**（归档→本地那条其实已经能用）；
  `LocalVolume::search` 底下是 `jwalk.skip_hidden(true)`，而 jwalk 0.9.0 的 `is_hidden` 就是
  `file_name.starts_with('.')`——**只看名字开头那个点，不看 Windows 的隐藏属性**（实测同：点开头的项搜不出来，
  只有隐藏属性的照常返回）；`RemoteVolume::search` 是明确的 `Unsupported`。
  笼统写成"搜索会漏隐藏件"会把一条已经能用的通路登记成待办，还会让人去修一个不存在的问题。
- 🔴 **"边收边写"当不了判据。** 我第一版门照"另一个句柄看到的文件大小"写，三轮才查出来：
  `write_all(...).await` **已经返回成功**之后，另开句柄问大小仍报 0 字节，
  要先在**写句柄**上做一次 `stream_position()`（seek）才变得可见。
  ⇒ 判据换成**写入次数**（`ops::stream_to_writer` 的计数 sink：三块流必须 ≥3 次写）。
  这条红过的是尺子，不是代码——记进 user 记忆「判据的输入必须是刚读到的」同族。
- 🔴 **源卷会被目标抢走**（接第 3 格时量出来的既有缺陷，不是这轮引入的）：`route_or_default`
  的样本清单把 `sources` 与 `dest_dir` **混在一起**看，而 `route_for` 取"最长的 id 前缀"，于是
  源在浅根、目标在深根时，**深根那个被选成了源卷**。探针实测（两个本地卷 `local:C:\a` 与
  `local:C:\a\b`，源 `local:C:\a\x.txt`、目标 `local:C:\a\b\out`）打印的是
  `PROBE 源卷=local:C:\a\b 目标卷=local:C:\a\b 同卷=true` ⇒ 跨卷那一步**根本走不到**，
  这次操作被冒充成了同卷搬运。
  🔴 **伤害面只量到这一层，别夸大**：浅根↔深根这种"两个都是本地卷"的组合，退回单卷 `copy`
  之后**盘上照样成功**（`LocalVolume` 本来就接受自己根之外的绝对路径）。这是变异复打给的证据：
  打"源卷又去看目标"这条刀口时，`fmnr-ai` 那条分派层门**照样绿**（它断言 done=1 与字节内容，
  两条都成立），只有新加的 volreg 那条判红。至于"源在错卷里解析 ⇒ NotFound 或搬错隔壁文件"，
  要的是**跨 kinds 的卷对**（本地卷的 id 得比归档卷的 id 更长才会抢赢），本机拿真 CLI
  注册不出那种形状 ⇒ **登记为未证**，不写成已验。
  修法是把"选源卷"独立成 `route_source(tool, args)`：`copy`/`move` **只看 `sources`**，
  其余工具与"没有 sources"的非法调用保持老规则（不动别的入口的含义）。
- **归档卷 `search` 的命中原来回读不了**（本轮顺手挖出的既有缺陷）：它吐
  `archive:<件>!/dir/deep.bin`，而 `key_of` 只认 `/`，于是 `fmnr cat "<命中>"` 得
  `io: 文件名、目录名或卷标语法不正确 (os error 123)`（实测）。工具对外给的坐标
  必须自己能解析 ⇒ `key_of` 现在认 `!/`，并有门（`search_hits_can_be_read_back`）。
- **探针自己会造故障（本轮两次）**：① 我从 shell 里抓 JSON 的 `archive:D:\\x` 当路径喂回去，
  双反斜杠是 JSON 转义不是真路径 ⇒ 误判"修了还是坏的"，改用 `python -c json.load` 解出真串才对；
  ② 测试助手 `MemVol::list` 在同一把非重入 `Mutex` 上锁两次 ⇒ `cargo test` 死锁不返回，
  表象是"构建很慢"，真相是尺子挂了。

### 🔴 第八个错只有 CI 能抓：门的**数据**是 Windows 专属的

`0a5eef0` 本地 gate 五步全绿、变异 25 条全判红，CI **两个 job 一起判红**（windows 2 条、ubuntu 6 条，
run 39207052882）。三条成因都是"本机只有一个平台 ⇒ 结构性缺口看不见"那一族的**新变体**：

1. **测试用 `format!("local:{}\\note.txt", root.display())` 拼源路径**——反斜杠在 unix 上不是分隔符，
   那条路径指向一个不存在的文件。⇒ 正解是 `root.join("note.txt").display()`：**让 `Path` 决定分隔符**，
   别自己拼。
2. **探针卷的 `inner()` 先 `replace('\\', "/")` 再 `trim_start_matches('/')`**——unix 上这把前导 `/` 削掉，
   得到一个**相对**路径，`root.join(...)` 拼出一个不存在的目录（ubuntu 报 `io: No such file or directory (os error 2)`）。
   本地 Windows 一点也看不出来：路径以盘符 `C:` 开头，**根本没有前导斜杠可削**。
3. **判据数据写死 `C:\Foo`** ⇒ 在 Linux 上 `Path::new("C:\\Foo").is_absolute()` 是 **false**，
   `route_for_dest` 在"绝对性"那一档就返回 None：`.expect("更深的根要赢")` 这类断言必判红，
   而更阴的是 `is_none()` 那类会**因为错误的原因**变绿——它量到的是绝对性检查，不是我要钉的目录成分规则。
   ⇒ 加 `n()` 助手按平台给真正的绝对路径；只有大小写归一那一条留在 `#[cfg(windows)]`
   （unix 上 `/USERS` 与 `/users` 是两个目录，写成跨平台断言会把"这里归一大小写"洗成平台事实）。

**规矩**：路径类判据动手前问三句——①分隔符是谁定的（该是 `Path`，不该是我拼的字符串）；
②这段路径在另一个平台上还**绝对**吗；③如果它在另一个平台先被别的闸门拦掉，我这条断言会不会
**因为错的原因**变绿。第③句是本轮最贵的：假绿比红难发现得多。

⚠ 修完这三条，两个 job **仍各红一条**（ubuntu 的 `copy_lands_on_the_other_volume`：回执
`done:1 / bytes:6`，可 `read` 拿到 `ENOENT`；windows 的 `move_is_not_special_cased…`：
`create_dir_all` 刚成功、紧接着 `write` 报 `ERROR_PATH_NOT_FOUND(3)`）。**那两条不是平台问题**，
真成因与对我的撤回写在下一条（第九）里——本机三遍不复现，别把它读成「不是缺陷」。

## 24. UI/UX 第一批：按键穿过输入框去动文件系统，与被拒操作的假回执（2026-10-19）

用户提法是「UI 太多的问题了」。这一批**不做观感**（DESIGN 的依赖口径：观感只靠布局与 `theme.rs` 令牌，
不新增依赖），只做"用户会被误导或丢数据"那一类。做法：先起真窗口 + 派一次只读排查，
再逐条自己复核 —— **没复核过的一条也不写进"已修"**。

### 修掉的两条（都有实测判据）

**① 六个输入框没登记「键盘归我」，快捷键穿过它们去动文件系统。**
`handle_keys` 的闸门读的是 `self.text_focus`（`app.rs` 里 `let typing = std::mem::take(&mut self.text_focus)`），
而这个标记原先**由各框自己 opt-in**。尺（可复算）：

```text
git show HEAD:crates/fmnr-ui/src/app.rs 里  TextEdit::singleline 出现 10 次
                                            self.text_focus = true 出现 3 次（另有一处 |=）
⇒ 10 个输入框里 6 个没登记：栏头地址框、挂载对话框那 4 个、包管理过滤框
```

后果（读代码得到的形状，不是猜的）：在挂载对话框里**贴路径时按 Ctrl+V** = 把剪贴板里的文件
贴进当前栏；**按退格改一个打错的盘符** = 栏跳到上级；**按 Delete** = 把选中那行送进回收站。
用户只是在编辑一段文字。

改法不是"把漏的六个补上"（那还是同一句政策写十遍，下一个框照样漏），而是**收成一处**：
新增 `text_edit(ui, te, &mut self.text_focus)`，十个框全走它，旧的自登记行删掉。
配两把尺：
- `every_text_edit_registers_keyboard_ownership`（静态）：数源码里的 `TextEdit::singleline`，
  每一处前后窗口里必须出现 `text_edit(` 与 `&mut self.text_focus`；**下限 10**（"看到 0 个"
  和"一个都没漏"输出一模一样）；先把整行注释抹成空白再数（否则它第一个红红在自己的说明上）；
  窗口切片走 `is_char_boundary`（中文源码按字节切会当场 panic —— 这把尺第一次跑就是这么红的）。
- 真窗口复验（`D:\tmp\ui` 语料）：打开「挂载」→ 点进输入框 → 打 `abc` → 按一次退格
  ⇒ 框里剩 `ab`，**两栏面包屑仍是 `D:\ › tmp › ui`**（截图为证）。

**② 被拒的操作照样宣布成功。**
`start_op` 被拒时（已有操作在跑 / 没挂卷 / spawn 失败）自己写了拒绝文案，
但**调用方紧接着又无条件**把状态栏盖成成功回执。三处实测在码：
`delete_selected` 无条件写「送入回收站（N 项，可恢复）…」、`paste` 与 `finish_drag` 用
`if self.running.is_some()` 当"我派发了吗"（上一个操作还在跑时它同样为真）、
重复清单更是**先** `dupes_dead.extend(..)` **再** `start_op(..)` ⇒ 被拒的那次行照样从清单消失、
"可省多少"跟着变小，而每一个文件都还在盘上。

改法是**把回执收进派发那一格**：`start_op(.., receipt: Option<&str>) -> bool`。
调用方拿不到"无条件写状态"的机会（不是加一条 if，而是让这件事写不出来），
需要"派出去了才记账"的地方（重复清单）用返回的 bool。
门：`a_refused_operation_must_not_announce_itself_as_done` —— 先占住"已有操作在跑"，
再按删除，断言状态栏说的是拒绝、且**不出现**「回收站」。

### 这一批**没动**的候选（各自的状态写清楚，别当下轮重扫）

## 二十五、UI 第二批：三条"判据问错了对象"的缺陷（提交待填）

而这件事的真答案在卷里 / 在另一栏里 / 在扫描那一刻的根上。**

### 修掉的三条（各带判据）

**① 冲突预筛问卷，不用 `Path::exists()`**（`app.rs:find_conflicts`）

旧格：`dest.join(name).exists()`。归档卷 / 远程卷上的 `dest` 不是一个能 `exists()` 的本地路径
⇒ 恒假 ⇒ 同名**永远进不了冲突弹窗**，操作带着默认政策直接跑完（`Skip` = 一个也不贴、界面也不说）。
新格：列**一次**目标父目录（`volume.list(dest, show_hidden:true)`）再按名字比，
口径与内核预遍历同一格（`transfer::entry_of`），所以"界面说没冲突、内核说有"不可能出现。
只列一次是刻意的：`entry_of` 每问一条 `list` 一遍，批量粘贴 N 项 = N 次全目录扫描，
在归档卷上每次都是 O(N)。
列不出来时**全部当冲突**（宁可弹窗问，不许静默替用户选政策）。

两条门（`volume_conflict_gate_tests`）：
- `a_conflict_on_an_archive_volume_is_detected_without_the_filesystem`：拿真夹具
  （`fmnr-archive/tests/fixtures/plain.7z`）挂进卷表，源写成"别处同名"，断言每一条都报冲突；
  外加一句**机制断言**——`dest.join(name).exists()` 必须为假，
  否则这扇门测不出"问卷 vs 探针"的差别（哪天有人把 `exists()` 加回来，这一句先红）。
- `an_unlistable_destination_asks_instead_of_assuming_no_conflict`：把普通文件当目录列，
  本地卷真的报错（这条前提也在门里），于是必须全部当冲突。

**② 「定位」之后活动栏跟着落点走**（`app.rs:reveal_in_panes`）

旧格只把目录 + 选中放到对栏，`active_pane` 还停在搜索前那一栏 ⇒ 面板收掉后按

换过根之后两半不同源，而界面上原先一个字的出处都没有。

## 二十七、局域网投递（手机 ↔ 电脑，单向丢文件）：新 crate `fmnr-share`

用户提法是"先搞传文件就可以了 局域网的"。摊开后定的两档：**两头都要**（手机投进来 +
电脑给出去）、鉴权走 **URL 带随机 token 的明文 HTTP**。落点=新 crate，不塞进 `fmnr-ui`
（"不要上帝模块"），也不塞进 `fmnr-ai`（那个 crate 的口径是"三条入口共用一张工具表"，
投递不是工具表上的一条）。

### 形状

- **上传**：`POST /put?k=<token>&n=<文件名>`，**请求体就是文件本身**。
  刻意不做 `multipart/form-data` —— 那要引 `multer`/`tokio-util` 的解析链，
  而页面是我们自己写的，`fetch(url, {body: file})` 就够了。名字走 `n=`（浏览器侧
  `encodeURIComponent`），服务端 `sanitize_name` **只取最后一段**再拒危险形态。
- **下载**：`GET /get?k=<token>&i=<编号>`。**只认编号，不认路径**——这一格是整块里
  最要紧的不变量：一旦允许调用方给路径，手机就成了整台机器的读取口。
  待取清单只装"用户在电脑上手动登记过的普通文件"（目录、不存在的路径一律不收）。
- **收件目录**固定 `下载/fmnr-收件`，**不是"当前栏那个目录"**：端口开着的时候落点要
  固定且预期内，不然同一个链接前后两次投的文件会散在两个地方。
- **同名不覆盖**：走全仓唯一那份命名规则（`ops::unique_name` → `core::rename`），
  打开走 `#61` 那道"拒写共享"闸。挑名字与写完之间整段串行（`create_lock`），
  否则两个手机同时投 `a.txt` 会互相 truncate。
- **绑地址**：默认 `127.0.0.1`；勾「允许局域网访问」才绑**本机那个局域网 IPv4**
  （不是 `0.0.0.0`——那只监听这一张网卡，比全盘开放窄）。闸从 `fmnr-ai::http::bind_addr`
  搬进 `fmnr_core::net::bind_addr`，两条腿共用同一格（同一句政策写两份一定有一份先过期）。

### 依赖账（量过，不是估的）

`cargo tree -p fmnr-ui -e normal` 唯一包数 **353 → 373**（+20：axum/tower/hyper-util 那一族）。
`git diff Cargo.lock` 只多 **1 条** `[[package]]`，就是本仓自己的 `fmnr-share`——
**第三方净增 0 条**（axum 早就在锁里给 `fmnr-ai` 用、`getrandom`/`tokio-util` 经
`russh` 那条链本来就在 UI 的图里）。⚠ exe 体积的差**没量**：要量得先把上一版重编一遍。

### 门：14 条，全在 `fmnr-share` 里，走真 handler / 真端口 / 真落盘

`oneshot` 打 handler（不起端口）+ 两个**真 socket** 门（`start()` 绑 `127.0.0.1:0`，
用 `std::net::TcpStream` 手写 HTTP/1.1，不引 HTTP 客户端）。覆盖：没 token 不给页面
也不许落盘、路径穿越削平到收件目录内、超长名截主干留扩展名、同名让路不覆盖、
超上限**不留半截文件**、`/get` 只认编号、页面 JS 指向存在的路由、关掉之后端口不再应答、
非回环没有显式批准就拒、链接里的地址**就是绑上的那个**。

变异复打 9 刀全判红、红的都是断言消息：M1 名字不削平 / M2 put 不验 token /
M3 同名不让路 / M4 超限留半截 / M5 编号不匹配也给第一个件 / M6 HTML 不转义 /
M7 上传路径上直接 join / M8 收到的件不报给界面 / M9 页面指到不存在的路由。
（M5 第一版打成 `.first()` 是**编译红**——`Iterator` 没这个方法——补成 `.next()` 才算。）

### 🔴 真窗口这一轮抓到的三件事，其中一件是我自己写下的错判

## 28. 安卓多状态收件（免装 app）+ 华为传输机制的接入面判定

用户口径：**"多种状态的、没有我这个软件的（手机侧不装 app）、我这个软件的都能收到、全系统都可以"**。

### 28-1 华为那套接不进来（三条实测判决，不是工作量问题）

| 实测 | 读数 | 后果 |
|---|---|---|
| 机型 | `Win32_ComputerSystem.Manufacturer = Micro-Star International`，`Model = MS-7E42`，台式 | 华为官方口径「非华为计算机不支持安装华为电脑管家」；一碰传 / 多屏协同 / 华为分享的 PC 端全是电脑管家的功能 ⇒ **入口不存在** |

| Wi-Fi Direct | `Get-NetAdapter` 里 Direct 适配器 **0 个**；WLAN（MT7925 Wi-Fi 7）`Disconnected`，联网走 Realtek 有线 | 华为数据面那层"绕过路由器"的前置本机不在 |

机制拆四层：① 发现（BLE advertising + NFC 贴牌带址）② 鉴权（`HiChain` 组可信群组，
OpenHarmony 侧要设备证书 + `ohos.permission.DISTRIBUTED_DATASYNC`）③ 数据面（Wi-Fi P2P）
④ UX（系统级常驻收件）。**第三方 Windows 程序拿不到 ②的证书链，手机也不会认它是可信对端**
⇒ "fmnr 加入现成超级终端会话"是假的。值得复刻的是 ①②④ 的体验，不是 ③ 的带宽。

局域网共享（SMB）这侧本轮量到：`LanmanServer` Running/Automatic、`445` 在听、
「文件和打印机共享」17 条启用规则**全部 `Profile=Private`**、入向 `Allow` 10 条、
以太网适配器类别 = Private，且已存在一个自定义共享 ⇒ 电脑本来就是个可用的 SMB 服务器。
但它只解决**手机当客户端取/写电脑**这一个方向：手机不会反过来把存储暴露成共享；
另外同名覆盖会**绕过 `#61` 那道闸**和唯一那份命名规则。**安卓各 ROM 文件管理器是否原生带
SMB 客户端：未证**，要用户在手机上验（入口 / 能否用 Windows 口令登 / 能否写）。

### 28-2 实际做的：给收件加第二条不跑脚本的腿

手机侧不装任何东西 ⇒ 唯一**任何安卓都有**的入口是浏览器。原来那一页只有
`fetch(...)`（JS + fetch 双依赖）；壳子浏览器禁 fetch、JS 坏了、或某些套壳 webview
里 `File` 对象进不去，那条腿就整条断。原生 `<form>` POST 是**不跑脚本也能发**的那条。

- `POST /send?k=`，`multipart/form-data`；页面两个按钮同一个收件目录、同名都让路。
- 🔴 **两条腿收敛到同一个 `ingest`**：让路 / 拒写共享 / 不留半截 / 报给界面只在收口实现一次。
  新通道若自己 `inbox.join(name)` 就废掉 `#61`。
- 多部分体是仓内手写的严格解析器：分隔符必须成行（串首或紧跟 CRLF）**且**尾随 CRLF/`--`，
  看不懂的形状当场停不猜；收尾截断只丢最后那块。**不引 `multipart` crate**（它的 default-on
  feature 会拖进 `multer`）。`/send` 是整块进内存（给小文档兜底），`/put` 才是流式 —— 这条
  差异写在函数注释里。**天花板分开**：`/send` 取 `min(hub.max_bytes, SEND_MAX_BYTES=64 MiB)`
  ——原来跟 `/put` 共用 2 GiB，那等于允许对面一句 POST 让本机缓冲 2 GiB；
  页面把"长视频走第一个按钮"直接写出来。
- 顺手抓到一个自伤：回执页把**文件名原样拼进 HTML**。已 `html_escape` 并补门。
  🔴 **上一版这条写重了，此处更正**（原文说"`<script>alert(1)</script>.txt` 就成了这台电脑

  `< > " | ? *`，带 `<script>` 的名字根本建不出文件 ⇒ 成功分支在本机是**碰巧安全**的

## 29. 投递常驻（可选开关）：同一把钥匙活过重启

用户口径：**"常驻可以选择打开和不打开"** ⇒ 做成一颗开关，默认关。

### 29-1 形状

- `fmnr-share::config::Prefs { enabled, lan, port, token }`，落在
  `<config>/fmnr/share.json`（Windows 是 `%APPDATA%\fmnr\share.json`）。
  `enabled` 就是那颗开/关按钮：开着 = 下次启动自动开，关掉 = 不再自动开。
- **端口也要留住**：只留 token 不够——端口一变，链接照样变，"书签还能用"就是假的。
  第一次开用系统挑的端口，开成之后写回；下次先试这个端口，**被占了才退回随机**，
  并且把"手机上的旧链接要换"说出来（静默改端口等于让人一直撞墙）。
- 🔴 **token 从文件读回来先验形状**（32 位小写十六进制）。手改过的、被别的程序写坏的、
  只有 3 个字符的，一律当没有、重新生成——**弱 token 比没有更糟**，它会让人以为"设过了"。
- 「换一把钥匙」：换完重启端口（旧 hub 里那把还在内存里），旧链接立刻 401。
- 写配置先写 `.tmp` 再改名：写到一半崩了，旧设置还在。

### 29-2 实测（三条判决性判据，都是文件/端口层面的）

| 状态 | 读数 |
|---|---|
| `enabled=true` 启动 | 配置被写回 `port: 61702`；`Get-NetTCPConnection` 显示在 `192.168.1.3:61702` 监听 |
| 同一把 token 取页面 | `curl` 带 token **200**、不带 **401**；拿到的就是那一页 |
| **重启**（换进程） | 配置仍是 `port: 61702` + 同一把 token；**同一条链接仍 200** |
| `enabled=false` 后重启 | 监听数 **0**；旧链接 **000**（连不上） |

⚠ 绑局域网地址时 `127.0.0.1` **连不上**（服务只绑那张网卡）。这是设计如此，
但第一次自测的人容易当场判成"没起来"——所以这里写明。

### 29-3 🔴 这轮自己踩的坑：门是绿的，exe 是旧的

前两次"自启没发生"的结论我都差点记成缺陷。真相是 `target/debug/fmnr-ui.exe`
的 mtime 还是 **10-20 04:03**，而源码是 **10-21 01:37**：`gate.sh` 跑的是

## 30. 第三条腿：WebDAV（把收件目录挂成盘）

用户口径：**「多个选择不就可以了吗 扩展巨大就行了」** ⇒ 不止"浏览器点链接"，再加一条
手机文件管理器能挂盘的协议面。

### 30-1 形状

- `GET/PUT/DELETE/PROPFIND/PROPPATCH/MKCOL/MOVE/LOCK/UNLOCK/OPTIONS` 挂在 `/dav` 与 `/dav/*`。
- 根 = `Hub::inbox`。路径**逐段**过 `sanitize_name`，且要求"原样返回"；`..`、盘符、
  分隔符、控制字符一律 403（**不压平**——压平是把越界写法悄悄改成合法落点）。
- 鉴权：Basic。**用户名随便填**，密码是 token；只给 token（无冒号）也认；`?k=` 也认（curl 手测）。
- **两套同名语义，刻意分开**：
  - 页面那两条腿 = 丢件 ⇒ 同名**让路**（`a (2).txt`）。
  - 盘 = 盘 ⇒ 同名 **PUT 覆盖**。
  覆盖不是"截断目标再写"，而是**写同目录临时件 `.part-<随机>` → 改名**：写到一半失败，
  旧件完好；改名那一刻才替换。临时件在 PROPFIND 里不列（`.` 开头一律跳过）。
- 🔴 `write_into` 是两条腿共用的写入口：丢件传 `unique_dest` 算好的目标，
  盘传 `inbox/<相对路径>`。**父目录必须已存在**（PUT 到不存在的目录 = 409），
  否则件会静默落到别处——这条是实测踩出来的：第一版 `ingest_exact` 只收名字，
  PUT `/dav/sub/x.txt` 落到了根上，MOVE 当场 409。
- 不引第三方 WebDAV 库：XML 手写转义，`base64` 用的是锁文件里**already 有**的 0.22.1
  ⇒ `Cargo.lock` 变的只是 `fmnr-share` 自己的依赖表，**第三方包净增 0**。

### 30-2 实测（真端口，curl）

| 动作 | 读数 |
|---|---|
| `OPTIONS /dav/` | 200；`DAV: 1, 2`；`Allow` 含 PROPFIND/PUT/GET/DELETE/MKCOL/MOVE |
| 错密码 | **401** |
| `PUT /dav/手机桌面.txt` | **201**；盘上出现 `手机桌面.txt` |
| 同名再 PUT | **201**；盘上内容变成第二次的；**仍然只有一个文件**（没有 `(2)`、没有 `.part`） |
| `GET` 同路径 | 回第二次的内容 |
| `PROPFIND Depth: 1` | 207；href 百分号编码、`displayname` 是中文原文 |

### 30-3 变异（7 把刀，全判红，无编译红）

D1 PUT 丢子目录 / D2 挂盘也用同名让路 / D3 认证不比密码 / D4 路径不逐段校验 /
D5 PROPFIND 不看 Depth / D6 暂存件不改名 / D7 临时件不隐藏。
脚本 `D:\tmp\mut_dav.py`（先自证基线绿）。D2 第一版写成单行 `unique_dest(&hub.inbox, last)`
是**编译红**（Arc move 后借用）——补成"先 let dest 再调"才算数。

### 30-4 没证到的

- **真手机上没挂过**：本机只用 curl 走完了协议动作。手机端文件管理器（各 ROM）是否
  认这套 PROPFIND/XML 形状、要不要 LOCK，**未证**。
- LOCK 是**假锁**：回一个像样的 lock-token 就完事，不做互斥。多人同时往同一路径写
  没有仲裁——自家网档位，写在界面上。
- Windows「映射网络驱动器」没试（它对 PROPFIND 的字段更挑）。
- PROPFIND 单目录最多列 2000 个孩子，超出部分静默截断（客户端看到的是"还有更多"吗？
  **未证**）。

## 31. 把 WebDAV 的 LOCK 做成真锁

用户口径：**"先补 LOCK 真互斥再推"**。上一版只回了一个像样的 `lock-token`，
两个客户端同时写同一路径**没有仲裁**——后写的把先写的悄悄盖掉，这正是 `#61` 那道闸
想挡的形状，只是换成了网络面。

### 31-1 语义

- 独占写锁，带**租期**：`Timeout: Second-N`（默认 900s、上限 8h）；到点的锁在
  每次访问时扫掉，不靠后台线程。
- 写操作（PUT/DELETE/MKCOL/MOVE）先问 `Hub::write_blocked_by`：被别人的锁盖住
  且请求里没有匹配的 `If: (<token>)` ⇒ **423 Locked**。
- **目录锁按"无限深度"罩孩子**；孩子此时**连加锁都加不上**——否则会出现
  "锁拿到了、却写不进去"的自相矛盾状态。
- `UNLOCK` 只认持有人那把：猜一个 token 不行（409），租期过了也不行。
- 锁表在 `Hub` 内存里：端口一关就没了。这是"自家网、单人"档位，不做跨进程持久锁。
- `LOCK` 也支持 **lock-null**（客户端先锁一个还不存在的路径再 PUT）——挂盘客户端常这么干。

### 31-2 实测（真端口 + curl）

| 动作 | 读数 |
|---|---|
| `LOCK /dav/lockme.txt` | 200，回 `Lock-Token: <urn:uuid:…>` |
| `PUT` 不带 `If:` | **423** |
| `PUT` 带 `If: (<token>)` | **201** |
| 同一路径再 `LOCK` | **423** |
| `UNLOCK` 错令牌 | **409** |
| `UNLOCK` 对令牌 | **204** |
| 解锁后再 `PUT` | **201** |

### 31-3 变异（5 把刀，全判红）

L1 锁不挡写 / L2 深度锁不区分子孙 / L3 加锁时不查已有锁 / L4 解锁不比令牌 /
L5 写入口根本不查锁。脚本 `D:\tmp\mut_lock.py`（先自证基线绿）。
🔴 **L3 第一轮是存活的**——它暴露了一个**真缺口**：测试只验了"祖先锁挡住写"，
没验"祖先锁挡住孩子**加锁**"。补了那条断言（§31-1 里那句）之后 L3 才判红。
⇒ 存活刀先当"测试缺口"查一遍，再谈等价变异。

### 31-4 没证到的

- **真手机上没挂过**（仍未证）：本机只用 curl 走完协议；各 ROM 的文件管理器
  会不会先 LOCK、认不认 423 的重试，没验。
- 锁只在内存：**fmnr 重启后锁全丢**。客户端若在重启期间还持有 token，会拿到 423
  ——大多数客户端会重新 LOCK，但这条没在真客户端上验。
- 没有 `LOCK` 的 `owner` 字段与 `DAV:owner` 显示（回的是固定形状）。
